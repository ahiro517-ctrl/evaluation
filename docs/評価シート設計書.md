# 花咲爺さんズ 評価・報酬 運用シート設計書

制度設計資料（2026年7月運用開始）をもとに、半期評価を実際に運用するための
Googleスプレッドシートと、それを生成・運用するGAS（Google Apps Script）の設計をまとめる。

- 対象制度: 半期ごとの評価（粗利・バリュー・スキル）と報酬（昇降給・昇格・降格）
- 評価対象: 正社員 ／ 社員に近い形で案件を担当するパートナーメンバー
- 評価サイクル: 前期（7月〜12月）／後期（1月〜6月）の半期単位
- 実装イメージ: GASが定数（マスタ）からスプレッドシートを自動生成し、入力→自動判定→会議用サマリまでを支援する

> 本書はまず「設計」を固めるためのもの。数値はすべて制度設計資料から転記している。
> 確定が必要な論点は末尾の「9. 確認したい論点」に整理した。

---

## 1. システム全体像

```
┌─────────────────────────────────────────────────────────┐
│  GAS（コードで管理する唯一の正）                          │
│   - constants.gs   制度の全マスタ（等級/判定/改定額 など） │
│   - build.gs       スプレッドシートとシート群を自動生成     │
│   - formulas.gs    各シートに計算式・入力規則を流し込む     │
│   - judge.gs       粗利倍率→判定、最終判定、昇降給を計算     │
│   - promote.gs     履歴を参照して昇格/降格の候補を判定       │
│   - menu.gs        スプレッドシート上のカスタムメニュー      │
└─────────────────────────────────────────────────────────┘
                          │ 生成・更新
                          ▼
┌─────────────────────────────────────────────────────────┐
│  Googleスプレッドシート（半期ごとに1ブック）               │
│   設定 / 名簿 / 粗利入力 / 案件明細 / バリュー評価 /         │
│   スキル評価 / 評価結果サマリ / 昇格・降格判定 / 履歴        │
└─────────────────────────────────────────────────────────┘
```

設計方針:

1. **制度の数値はGASの `constants.gs` を唯一の正とする。** スプレッドシート上の
   「設定」シートはそこから書き出された参照用。制度変更はコードを直して再生成する。
2. **判定ロジックは原則スプレッドシートの数式で完結させる**（誰が見ても追える）。
   履歴をまたぐ昇格/降格の連続判定だけはGASで計算する。
3. **1半期 = 1ブック**。期をまたぐ判定は「履歴」シート（前期までの確定値）で連結する。
4. 入力は「自己評価 → ユニット長評価 → 評価会議調整」の3段で、最終列は評価会議が確定する。

## 2. 評価の流れ（制度サマリ）

```
粗利実績 ──→ 粗利倍率 = 実績半期粗利 ÷ 半期基準粗利 ──→ 粗利判定(S〜F)
                                                              │
バリュー9項目(27点満点) ──→ バリュー判定(高い/標準/要改善) ──┤
                                                              ▼
                                       昇降給マトリクスで最終判定(S〜F)
                                                              │
                              ┌───────────────┬──────────────┘
                              ▼               ▼
                        改定額（昇降給）   昇格・降格判定（履歴＋スキル＋意思）
                              │
                              ▼
                        改定後月給 → 2月25日振込（1月給与分から反映）

※ スキル評価は昇給額には使わない。昇格判断と次のアサインに使う。
```

## 3. スプレッドシート構成（シート一覧）

| # | シート名 | 役割 | 主な入力者 |
|---|----------|------|-----------|
| 1 | `設定` | 制度マスタの参照用書き出し（編集はGAS側） | システム（自動） |
| 2 | `名簿` | メンバーの等級・月給・年次・区分など | 管理者 |
| 3 | `案件明細`（任意） | 案件ごとの粗利配分の内訳 | 案件メイン担当 |
| 4 | `粗利入力` | 半期粗利の確定値と自動の倍率・判定 | 担当者入力→経理確定 |
| 5 | `バリュー評価` | 9項目の点数（自己／ユニット長） | 本人・ユニット長 |
| 6 | `スキル評価` | 10項目の1〜5（自己／ユニット長） | 本人・ユニット長 |
| 7 | `評価結果サマリ` | 全判定・最終判定・改定額・改定後月給 | システム（自動）＋会議調整 |
| 8 | `昇格・降格判定` | 履歴を参照した候補判定とチェックリスト | システム＋評価会議 |
| 9 | `履歴` | 過去半期の確定判定（連続条件の判定に使用） | システム（確定時に追記） |

各シートには先頭に `社員ID`・`氏名`・`等級` を置き、`社員ID` をキーに `名簿` と紐づける
（`VLOOKUP`/`XLOOKUP` で参照）。

## 4. マスタ定義（`設定`シート＝`constants.gs`）

### 4-1. 等級基準テーブル

`半期基準粗利`（＝倍率1.0倍の額）と `半期目標粗利`（＝3.0倍＝判定A下限）。
A・L・M は「基準月収（レンジ下限）× 6か月」が基準粗利。B は年次別の固定。

| 等級 | 月収レンジ | 基準月収 | 半期基準粗利(1.0倍) | 半期目標粗利(3.0倍) | 等級グループ |
|------|-----------|---------|--------------------|--------------------|-------------|
| B（1年目） | 240,000〜280,000 | — | 166,667 | 500,000 | B・A |
| B（2年目） | 240,000〜280,000 | — | 500,000 | 1,500,000 | B・A |
| B（3年目〜） | 240,000〜280,000 | — | 833,334 | 2,500,000 | B・A |
| A1 | 300,000〜349,000 | 300,000 | 1,800,000 | 5,400,000 | B・A |
| A2 | 350,000〜400,000 | 350,000 | 2,100,000 | 6,300,000 | B・A |
| L1 | 450,000〜499,000 | 450,000 | 2,700,000 | 8,100,000 | L・M |
| L2 | 500,000〜550,000 | 500,000 | 3,000,000 | 9,000,000 | L・M |
| M1 | 600,000〜649,000 | 600,000 | 3,600,000 | 10,800,000 | L・M |
| M2 | 650,000〜700,000 | 650,000 | 3,900,000 | 11,700,000 | L・M |

- `A1→A2` などは等級内の昇給で、昇格ではない。昇格は B・A・L・M 間の移動。
- B等級は育成段階のため固定目標。倍率は規模感をつかむ参考値として扱う。

### 4-2. 粗利判定テーブル（倍率→判定）

| 判定 | 倍率（下限以上〜上限未満） | 状態 |
|------|--------------------------|------|
| S | 3.5 〜 | 目標を大きく超えている |
| A | 3.0 〜 3.5 | 目標を達成している |
| B | 2.5 〜 3.0 | 目標に近い水準 |
| C | 2.0 〜 2.5 | 据え置き水準 |
| D | 1.5 〜 2.0 | 改善が必要 |
| E | 1.0 〜 1.5 | 大きく改善が必要 |
| F | 〜 1.0 | 大きく不足している |

### 4-3. バリュー評価（9項目 × 3点 = 27点満点）

項目: 信頼／疑問／熱量／創造／実行速度／主体性／チームワーク／挑戦／責任

| バリュー判定 | 合計得点 | 状態 |
|-------------|---------|------|
| 高い | 23〜27 | 価値観に沿った行動が安定 |
| 標準 | 17〜22 | 期待水準 |
| 要改善 | 9〜16 | 行動面で改善が必要 |

### 4-4. スキル評価（10項目 × レベル1〜5）

項目: 全体管理／予算管理／企画／PR・集客／クリエイティブ／事務局／運営制作／進行制作／運営現場／進行現場

| レベル | 言葉 | 意味 |
|-------|------|------|
| 1 | 学習中 | 学びながら補助する段階 |
| 2 | 補助担当 | 指示を受け、限定範囲を担当 |
| 3 | 基本担当 | 基本業務を大きな穴なく担当 |
| 4 | 主担当 | 標準的な案件を主担当で任せられる |
| 5 | 高度担当 | 難易度の高い案件・判断を任せられる |

スキルは昇給額には使わず、昇格判断と次のアサインの材料に使う。

### 4-5. 昇降給マトリクス（粗利判定 × バリュー判定 → 最終判定）

| 粗利判定＼バリュー | 要改善 | 標準 | 高い |
|------------------|:------:|:----:|:----:|
| S | A | S | S |
| A | B | A | S |
| B | C | B | A |
| C | D | C | B |
| D | E | D | D |
| E | F | E | E |
| F | F | F | F |

### 4-6. 改定額テーブル（最終判定 × 等級グループ → 月給改定額）

| 最終判定 | B・A等級 | L・M等級 |
|---------|---------:|---------:|
| S | +12,000 | +18,000 |
| A | +8,000 | +12,000 |
| B | +4,000 | +6,000 |
| C | ±0 | ±0 |
| D | -4,000 | -6,000 |
| E | -8,000 | -12,000 |
| F | -12,000 | -18,000 |

- 昇給は積み上がる（判定Aを年2回で月給 +16,000、年収ベース約 +19万円）。
- 昇給と昇格が同時に成立する場合は昇格を優先し、合算しない。

### 4-7. 昇格条件（A等級への昇格）

| 要素 | 条件 |
|------|------|
| 粗利 | ①判定A以上が3期連続 ／ ②判定Sが2期連続 |
| バリュー | バリュー判定が標準以上 |
| スキル | 全10項目が3以上 ／ 制作・現場で4以上の強み |
| 本人意思 | A等級で求められる役割に挑戦する意思 |
| 評価会議 | 昇格後のアサイン・支援体制を用意できる |

昇格すると新しい等級レンジの下限から始まる。

### 4-8. 降格条件

| 見るもの | 降格対象となる状態 |
|---------|------------------|
| 粗利 | 粗利判定が半期2回連続で判定D以下 |
| バリュー | バリュー判定が半期2回連続で要改善 |
| スキル | 「1（学習中）」または「2（補助担当）」が半期2回連続で残る |
| 改善状況 | 支援後の次半期でも十分な回復が見られない |

降格時の給与は降格先等級のレンジ上限に合わせる（例: A→B なら B上限の28万円から再スタート）。
降格後は降格先の等級基準で評価し、再度昇格基準を満たすまでその等級に滞留する。

### 4-9. パートナーメンバー報酬

| 案 | 内容 | 見直し条件 |
|----|------|-----------|
| 案A: 粗利シェア型 | 報酬＝確認した粗利の50% | 粗利連動のため3倍/1.8倍の見直しは置かない |
| 案B: 固定報酬＋モニタリング | 報酬は固定で合意 | 半期ごとに 粗利÷報酬 を確認。2期連続3倍超で上方、1期1.8倍以下で下方見直し |

どちらも担当案件の粗利を社員と同様に申告・確認する前提。

### 4-10. 案件粗利の社内固定単価（現場稼働控除用）

| 稼働内容 | 社内固定単価 |
|---------|-------------|
| ディレクター | 50,000円／日 |
| アシスタントディレクター | 35,000円／日 |
| スタッフ | 25,000円／日 |

クライアント見積とは別の社内ルール。詳細ルールと入力ツールは別途整理。

## 6. 主要な計算ロジック

### 6-1. 粗利倍率と判定（数式）

```
粗利倍率 = 実績半期粗利 / 半期基準粗利
粗利判定 = LOOKUP(粗利倍率, {0,1.0,1.5,2.0,2.5,3.0,3.5}, {"F","E","D","C","B","A","S"})
```

B等級は固定目標が評価の本体。倍率は参考列として併記する。

### 6-2. バリュー判定

```
バリュー判定 = IFS(合計>=23,"高い", 合計>=17,"標準", TRUE,"要改善")
```

### 6-3. 最終判定（昇降給マトリクス）

2次元表（4-5）を `設定` に置き、`INDEX/MATCH` で
`(粗利判定行, バリュー判定列)` を引く。

### 6-4. 改定額・改定後月給

```
改定額 = INDEX(改定額表, MATCH(最終判定), MATCH(等級グループ))
改定後月給 = 現在月給 + 改定額
（昇格が成立する場合は改定額を合算せず、昇格後レンジ下限を採用）
```

### 6-5. 昇格・降格（GASで履歴連結）

- 昇格粗利条件: 直近履歴を新しい順に並べ、「A以上が3期連続」または「Sが2期連続」を判定。
- 降格条件: 「判定D以下が2期連続」「要改善が2期連続」「スキル1・2が2期連続残存」を判定。
- いずれも一度の評価で確定せず、評価会議で最終判断（シート上は「候補」として提示）。

## 7. 運用フローとスケジュール

制度資料のスケジュール（後期＝1月〜6月の確定例）に沿う。

| 時期 | 作業 | シート操作 |
|------|------|-----------|
| 翌1月 第1週 | 自己評価（約1週間） | 本人が `バリュー`/`スキル` の自己列を入力 |
| 翌1月 第2週 | ユニット長評価（約1週間） | ユニット長が長評価列を入力 |
| 並行 | 粗利の確定 | 担当者入力→経理が `粗利入力` を確定 |
| 1月後半〜2月前半 | 面談（約2週間／1人1時間） | `評価結果サマリ` を見ながら対話 |
| 2月前半〜2/15 | 評価会議（経営2回程度） | 確定列・最終判定・昇格降格を確定 |
| 2/15まで | 評価確定 | GASで `履歴` へ追記、ブックをロック |
| 2/25 | 振込 | 1月給与分から反映（間に合わない場合は遡及） |

面談で具体化するもの: 自分の粗利／不足要素／次に取り組むこと／伸ばすスキル／必要な案件経験／求めるサポート。

## 8. GASモジュール構成（実装予定）

| ファイル | 関数（例） | 役割 |
|---------|-----------|------|
| `constants.gs` | `GRADES`, `GP_JUDGE`, `VALUE_ITEMS`, `SKILL_ITEMS`, `PAY_MATRIX`, `RAISE_TABLE` | 制度マスタの定数 |
| `build.gs` | `buildWorkbook(period)`, `createSheet_*()` | ブック／シート生成、見出し・体裁 |
| `formulas.gs` | `applyFormulas_()`, `applyValidation_()` | 計算式・入力規則（ドロップダウン）注入 |
| `judge.gs` | `recalcAll_()` | 倍率・各判定・改定額の再計算（数式で足りない補助） |
| `promote.gs` | `evaluatePromotion_()`, `evaluateDemotion_()` | 履歴参照の連続判定 |
| `history.gs` | `commitPeriod_(period)` | 確定値を `履歴` へ追記、ロック |
| `menu.gs` | `onOpen()` | 「評価運用」カスタムメニュー（生成／再計算／確定） |

カスタムメニュー想定: 「新しい半期ブックを作成」「名簿から各シート展開」「再計算」「昇格・降格を判定」「当期を確定して履歴へ」。

## 9. 確認したい論点（設計確定のため）

実装に入る前に、以下を決めたい。現状は資料に沿った既定値で設計している。

1. **粗利の基準月収**: 倍率の分母（半期基準粗利）は資料どおり「等級レンジ下限 × 6」で固定でよいか。
   それとも個人の現在月給ベースにするか（資料の早見表は等級下限ベース）。
2. **バリュー／スキルの最終確定値**: 自己とユニット長の2系統入力で、確定は「ユニット長評価」を既定にしてよいか。
   評価会議での上書きを許す前提でよいか。
3. **改定後月給のレンジ運用**: 昇給がレンジ上限を超える場合の扱い（上限で頭打ち→昇格検討、など）。
4. **パートナーメンバー**: 案A／案Bは個人ごとに選択でよいか。シート上で報酬計算まで自動化するか、モニタリング表示までにとどめるか。
5. **データ範囲・人数規模**: 1ブックの想定人数（数式レンジの確保のため）。
6. **配布形態**: スタンドアロンGAS（ライブラリ）か、テンプレートブックにバインドしたスクリプトか。
